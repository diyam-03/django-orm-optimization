      Where the slow queries go

        The fix is two extra words on the queryset

        select_related joins the table

        A country has exactly one region, so the region comes back in the same query as the country, through a SQL JOIN. Use it for foreign keys and one-to-one links.

        prefetch_related batches the lookups

        A country has many languages, so a join would repeat every country row. Django instead runs one extra query for all the languages at once and matches them to countries in Python. Use it for many-to-many and reverse foreign keys.

        Research answers

        What is the N+1 problem?

        You run 1 query to get a list of N items, then 1 more query for each item to get something related to it, so N+1 queries in total. In Django it hides in innocent code such as country.region.name inside a loop or a serializer. It is harmless with 10 rows and painful with 10,000, because every query pays a network round trip and parsing cost, even when each one is tiny.

        select_related vs prefetch_related

        select_related follows single-valued links (foreign key, one-to-one) and loads them with a JOIN in the same query. prefetch_related handles multi-valued links (many-to-many, reverse foreign key): it runs one separate query per relationship using WHERE id IN (...), then joins the results in Python. Result in this project: 1 + 3N queries become 3.

        How does an index speed up a query, and what does it cost?

        Without an index PostgreSQL reads every row (a sequential scan). An index is a sorted structure, a B-tree, that lets it jump to matching rows, like the index at the back of a book. The cost: extra disk space for each index, and slower INSERT, UPDATE and DELETE because every index must be updated too. Index the columns you filter or sort by often, not everything.
